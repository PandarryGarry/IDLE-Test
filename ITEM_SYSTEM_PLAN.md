# Система предметов Aethelia — план и контракт

> **Статус:** черновик плана, согласуется с владельцем. Кода по этому документу нет.
> Дата: 2026-09-06. Канон чата: `NEXT_CHAT_HANDOFF.md`.

---

## 1. Цель и принципы

Вводим **800+ иконок предметов** в игру через единый каталог, привязанный к данным,
с **тирами**. Не «впиливаем картинки поверх» — сначала фундамент, потом подключение.

Зафиксировано с владельцем:

- **Greenfield.** Старые id предметов не сохраняем. Игроков нет, владелец создаст
  нового персонажа. Никаких alias-слоёв и совместимости со старым `save_data`.
- **Тир — данное поле** (1–12), источник истины — имя папки/файла картинки (`t05`).
  **Грейд добавляем позже** (отдельное поле), сначала разберёмся с тиром.
- **Язык — русский.** Весь контент предметов по-русски; английский позже через i18n.
- **Каталог — в репозитории** + закладываем фундамент миграции на БД.
- **Картинки — только WebP через `iconUrl()`**, никогда `.png` в `<img>`.
- **Вывеска каталог не греет** (правило `lib/bootPreload.ts` не меняется).

---

## 2. Конвейер картинок (закон)

Канон: `scripts/assets/README.md`.

| Слой | Что | Правило |
|---|---|---|
| Мастер | PNG 1024×1024 (~300 КБ) в `public/assets/icons` | в `<img>` никогда |
| Рантайм | соседний `.webp` (иконки 256px, аватары 384px) | через `iconUrl()` |
| Сборка | `node scripts/assets/optimize.mjs` | повтор пропускает свежие, `--force` пересобирает |

- `iconUrl('weapons/sword_1h/t05')` → `/assets/icons/weapons/sword_1h/t05.webp`.
- Сотни иконок в WebP ≈ единицы мегабайт вместо ~300 МБ мастеров; иконка 256px ≈ 4–6 КБ.
- Предметы подгружаются лениво (`loading="lazy"`), **не на вывеске**.
- Валидатор каталога (см. §9) дополнительно проверяет наличие `.webp`.

## 3. Модель предмета

```ts
interface Item {
  id: string;              // стабильный ключ вызовов/взаимодействий (§5)
  name: string;            // русское название
  description: string;     // русское описание (обязательно)
  category: ItemCategory;  // resource/weapon/armor/jewelry/tool/consumable/loot…
  tier: 1 | 2 | … | 12;    // качество/«уровень» (§4)
  grade?: Grade;           // РЕЗЕРВ: цвет ранга — добавим позже
  equipSlot?: EquipSlot;   // для экипа/бижи
  stats?: ItemStats;       // РЕЗЕРВ структуры; значения — отдельным шагом
  maxDurability?: number;  // прочность в каталоге (механика позже)
  stackable: boolean;
  twoHanded?: boolean;
  heal?: number;           // еда/зелья
  sellValue: number;       // экономика позже
  buyValue?: number;
  iconPath: string;        // путь БЕЗ расширения, например 'weapons/sword_1h/t05'
  recipe?: RecipeRef[];    // РЕЗЕРВ: из чего крафтится (§6)
  source?: SourceRef;      // РЕЗЕРВ: farm/craft/shop/quest/boss (§6)
}
```

Примечания:

- **Текущая прочность** живёт не в каталоге, а в состоянии игрока (инвентарь/сейв).
- `grade`, `stats` (значения), `recipe`, `source` — поля закладываем сразу, наполняем
  в следующих батчах. Добавлять поле в централизованный каталог потом — дёшево,
  но структуру лучше сразу иметь правильной.
- Сейчас у 113 легаси-предметов `description` отсутствует у всех (0/113) — в новой
  модели описание обязательно с первого предмета.

## 4. Тиры

**Тир = качество и «уровень» предмета.** Тир 1 — слабый, тир 12 — сильнейший.
Больше тир → тяжелее фарм/крафт и заметно выше характеристики.

- Тиры **1–8** фармятся в базовых локациях.
- Тиры **9–12** — дальние/особые локации (на картинках прорисованы в отдельном
  стиле: пурпур/фиолет/кроваво-красный).
- Инструмент тира N фармит/крафтит предметы тира ≤ N; выше тир инструмента —
  быстрее фарм/крафт. Первый тир инструментов — покупка/квест, дальше — крафт.
- Экип тира 12 невозможен без материалов тира 12 (единый граф «фарм → крафт → экип»).

**Лестница металлов** (по цвету слитков `materials/metals/ingot_t01…t12`,
ПРЕДВАРИТЕЛЬНО — владелец подтверждает глазами):

| Тир | Цвет на диске | Металл |
|---|---|---|
| t01 | оранжевый | медь |
| t02 | бронзовый | бронза |
| t03 | серо-синий | железо |
| t04 | серебро | сталь |
| t05 | жёлтый | золото |
| t06 | глубокий синий | мифрил |
| t07 | циан | рунит |
| t08 | зелёный | адамантит |
| t09 | тёмно-красный | дракон |
| t10–12 | пурпур/фиолет/кровь | экзотика (дальние локации) |

- Дерево/руда/рыба — та же 12-ступенчатая логика; у рыбы на диске `fish_01…25`
  (в батче 1 вводим 12, 13–25 — запас).
- Бижа пронумерована `v01…v15` (пояса/ожерелья), `v01…v10` (кольца/браслеты):
  первые 12 = тиры, дальше — уникальные (уточним, когда будем смотреть папки глазами).
- `weapons/unique/*` — уникальный лут с элитных/мировых боссов: другой визуал,
  характеристики близкие к тир-12 (не сильнее), плюс бонусы/эффекты.

**Грейд** — отложен. Задача грейда: цвет-маркер ранга. В игре уже есть 6-цветная
«редкость» (рамки слотов `ui/slots/*`, точки в углу). Свести «12 цветов тиров» и
«6 цветов редкости» в одну логику — отдельное решение, после тиров.

## 5. ID-схема (greenfield)

- `lower_snake_case`, ASCII, стабильный и человекочитаемый.
- Префикс = семейство (`log_`, `ore_`, `bar_`, `fish_`, `sword_`, `helm_`, …) —
  группировка и сортировка.
- **Число тира в id не дублируем** (тир — отдельное поле); число остаётся в имени
  файла картинки и сверяется валидатором.
- У предметов без «материала» (анонимная бижа/уникальные) номер тира допускается
  прямо в id (`necklace_t05`, `unique_sword_01`).

Примеры (батч 1):

```
log_normal (t1) … log_redwood (t8) … log_<экзотик> (t9–12)
ore_copper (t1) … ore_dragon (t9) … ore_<экзотик> (t10–12)
bar_copper (t1) … bar_dragon (t9) … bar_<экзотик> (t10–12)
fish_shrimp_raw / fish_shrimp_cooked (fish_01) … fish_whale_* (fish_12)
coal, stone
```

Оружие/броня/бижа в своих батчах следуют той же схеме
(`sword_1h_copper`, `helm_plate_copper`, `helm_cloth_t01`, …).

## 6. Структура каталога

Не один большой файл — дерево папок. Точечная правка = свой файл.

```
src/domain/items/
├── index.ts            # публичное API: getItem() / getAllItems() + сборка в Map
├── types.ts            # Item, ItemCategory, ItemTier, ItemStats, …
├── catalog/
│   ├── resources/      # фарм-база
│   │   ├── logs.ts     #   log_t01…t12
│   │   ├── ores.ts     #   ore_t01…t12
│   │   ├── bars.ts     #   ingot_t01…t12
│   │   ├── fish.ts     #   fish_01…12 raw/cooked
│   │   └── minerals.ts #   stone, coal
│   ├── foraging/       # «Сбор»
│   │   ├── wood.ts     #   ветки/палки/шишки/листья
│   │   ├── fungi.ts    #   грибы raw/cooked
│   │   └── bits.ts     #   песок, волокно, …
│   ├── weapons/        # swords/axes/bows/staves/daggers/scythes/shields (позже)
│   ├── armor/          # cloth/leather/plate (позже)
│   ├── jewelry/        # necklaces/rings/belts/bracelets (позже)
│   ├── tools/          # инструменты (позже)
│   ├── unique/         # лут с боссов (позже)
│   └── consumables/    # готовые блюда, зелья (позже)
├── equipmentStats.ts   # (существующий, остаётся)
└── gearSets.ts         # (существующий, остаётся)
```

Правила:

- Каждый файл = типизированный массив `Item[]` одного семейства.
- `index.ts` собирает всё в `Map<id, Item>`; UI/логика обращаются только через
  `getItem(id)` — замена источника (репо → БД) коснётся одного модуля.

## 8. Хранение: каталог в репо + фундамент миграции на БД

**Каталог** (одинаков для всех, read-only) — версионированный код в репозитории.
На вместимость игры это не влияет: 800 определений читаются один раз, а не на
каждое действие.

**Фундамент миграции** (закладываем сейчас, таблиц не создаём):

1. **Стабильные id** — контракт с `save_data` и будущей БД.
2. **Единственная точка доступа** `getItem(id)` + интерфейс каталога.
3. **Строгая схема** (в workspace уже есть `zod` / `lib/api-zod`) — та же схема
   позже посеет таблицу `items` без переписывания.
4. **`version` каталога** — кэш/обновления.

**Состояние игрока** (сумка/надето/прочность) — как сейчас, в облаке
`characters.save_data` (jsonb), локально только временный кэш. Нагрузку при росте
игроков создаёт состояние, а не каталог; idle-тики считаются на клиенте, сервер
видит периодические снапшоты (~3 мин + pagehide) — это легко выдерживает тысячи
игроков. Перенос в таблицу `items` / нормализацию инвентаря делаем вместе с
серверной логикой (торговля/экономика/античит), тогда же.

**Greenfield-следствие:** новая версия `save_data`; старые id не поддерживаются,
владелец начинает нового персонажа. Мигратор старых предметов не нужен.

## 9. Валидатор каталога (скрипт, как `typecheck`)

Проверяет перед мержем:

- у каждой записи `iconPath` существует `.webp` на диске;
- нет «осиротевших» картинок без записи (отчёт);
- `tier` совпадает с числом в имени файла (`t05` ↔ tier 5);
- id уникальны, `description` не пустой;
- если лежит только мастер-PNG без `.webp` — подсказка «запусти `optimize.mjs`».

## 15. Данные-как-контент + админ-панель (видение)

Владелец хочет: точечно редактировать предметы/экип/навыки/профессии и баланс без
лезания в код — через админ-панель (роль `admin` в `profiles` уже есть).

Следствие: **весь изменяемый контент — данные со стабильными id**, а не строки в
компонентах и не хардкод в обработчиках.

### Текущее состояние (контент разбросан)

- имена/описания навыков — в `lib/i18n.ts`;
- действия (деревья/камни/рецепты) — в `domain/professions/*.ts`;
- логика обработки — в `core/skillRegistry.ts`;
- привязка профессия→столп — в `data/balance/professions.ts`;
- иконки навыков — эмодзи в `shared/icons/skillIcons.ts`.

### Целевая модель (единый источник)

- `SkillConfig` — id, nameRu, descriptionRu, category, кривая XP, иконка, список действий;
- `ActionConfig` — id, nameRu, level, xp, interval, выход, требования (вместо
  `WoodcuttingTree`/`MiningRock`/… — те же данные, но в общем виде);
- `ProfessionConfig` — id, столп/ветвь, бонусы (расширить `PROFESSION_FEEDS`);
- иконка навыка — поле-данные (сейчас эмодзи; картинки `skills/*.webp` на диске есть,
  соответствие уточним).

Файлы по группам в `data/content/…` (или расширенный `data/balance/`), как у предметов.
Имена/описания контента — в конфиге (`nameRu`/`descriptionRu`), а `i18n` остаётся
только для статичного UI.

### Правки «без деплоя» = оверлей в БД

Чтобы админ-панель меняла значения на лету, редактируемые значения должны лежать
(или переопределяться) в БД. Паттерн:

- **база** — версионированный контент в репо (офлайн, ревью, валидатор);
- **`config_overrides`** (таблица Supabase) — дельта-правки админа по id;
- **рантайм** — `merge(base, overrides)` по id.

Каталог/баланс остаются в репо как источник истины; админка пишет только дельты.
Полный перенос каталога в БД при этом не обязателен.

### Что НЕ входит сейчас

- сама админ-панель (отдельный этап, на `admin`-роли);
- нормализация инвентаря / экономика / античит (вместе с ними — БД).

### Правило на все батчи

Любая новая механика приходит с конфигом-данными, а не хардкодом: предметы,
действия, награды, бонусы, рейты — всё по id, всё в data-файлах.
