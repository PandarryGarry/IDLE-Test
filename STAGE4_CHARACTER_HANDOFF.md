## 1. Модель персонажа (главные решения)

- **Один персонаж на аккаунт.** Создание нового персонажа **жёстко удаляет** старого
  (персонаж + весь его инвентарь/прогресс). Это убирает лазейку «оффлайн-фарма» и
  мультипликатор экономики (нельзя качать 3 персов одновременно).
- **Раса + аватар.** Выбор **двухступенчатый**:
  1. **Раса** (1 из 5): `human`, `elf`, `dwarf`, `orc`, `beastfolk`. На карточке расы
     показываются её **бонусы** (2 положительных + 1 отрицательный).
  2. **Аватар** — **ровно 6 аватаров выбранной расы**
     (`avatars/<race>/<race>_{male,female}_01..03.png`).
  Перевыбор расы возможен **на лету** (без потери введённого ника), пока персонаж не подтверждён.
- **Никнейм = персонажу** (не аккаунту). Поле «Имя» из регистрации **убираем**. Ник вводится
  при создании персонажа. Уникальность — **глобальная** (среди всех игроков), через RPC.
- **Бонусы расы — только структура** («2+ / 1−»), конкретные числа/статы настраиваем позже,
  когда появится система характеристик. Сейчас влияния на формулы **нет**.

## 2. Данные персонажа

```ts
interface Character {
  id: string;
  userId: string;          // FK → profiles.id (auth.users.id)
  nickname: string;        // глобально уникален
  avatarId: string;        // 'human_male_01' и т.д. (путь в avatars/<race>/)
  raceId: string;          // 'human' | 'elf' | 'dwarf' | 'orc' | 'beastfolk'
  saveData: string;        // jsonb — инвентарь, навыки, оборудование, gp, maxSlots, ...
  lastSavedAt: number;
  createdAt: number;
  hasChangedNickname: boolean;   // «1 раз бесплатно»
  hasChangedAvatar: boolean;     // «1 раз бесплатно»
  isDeleted: boolean;            // мягкое удаление (TTL 1 месяц)
  deletedAt: number | null;
}
```

## 3. Аккаунт (таблица `profiles`) — отдельно от персонажа

Аккаунт и персонаж хранятся **в разных таблицах** — так проще управлять в БД и через
будущую админ-панель, и изменения (напр. донат-валюта) сразу применимы в игре.

```sql
profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  email text,
  role text default 'user',            -- 'user' | 'admin'  (задел под админ-панель)
  rules_accepted_at timestamptz,       -- когда принял правила
  rules_version text,                  -- версия правил (для повторного согласия)
  donate_currency bigint default 0,    -- ДОНАТ-ВАЛЮТА НА АККАУНТЕ (не перс)
  selected_character_id uuid,          -- активный персонаж
  created_at timestamptz default now(),
  updated_at timestamptz default now()
)
```

- **Донат-валюта привязана к аккаунту**, НЕ к персонажу: при удалении персонажа
  она не теряется.
- **`role`** — отметка администратора (сейчас просто флаг; админ-панель позже).
- **`rules_accepted_at` + `rules_version`** — окно правил.

## 4. Схема Supabase (SQL)

Таблица персонажей:

```sql
create table if not exists public.characters (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  nickname text not null,
  avatar_id text not null,
  race_id text not null,
  save_data jsonb default '{}'::jsonb,
  last_saved_at timestamptz default now(),
  created_at timestamptz default now(),
  has_changed_nickname boolean default false,
  has_changed_avatar boolean default false,
  is_deleted boolean default false,
  deleted_at timestamptz
);
create unique index if not exists characters_nickname_key on public.characters (nickname)
  where not is_deleted;  -- глобальная уникальность ника среди «живых»
```

RLS + политики:

```sql
alter table public.characters enable row level security;

create policy "Users manage own characters"
  on public.characters for all
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

RPC проверки уникальности ника (обходит RLS — security definer):

```sql
create or replace function public.is_nickname_taken(candidate text)
returns boolean
language sql security definer set search_path = public
as $$
  select exists (
    select 1 from public.characters
    where lower(nickname) = lower(candidate) and not is_deleted
  );
$$;
```

Поля `rules_accepted_at`, `rules_version`, `role`, `donate_currency`,
`selected_character_id` — добавить в `profiles` (при наличии) или хранить в
`user_metadata` (fallback на этом этапе).

## 5. Сохранение — трёхуровневая схема

| Уровень | Когда | Куда | Зачем |
|---|---|---|---|
| Память | каждый тик | zustand | мгновенный UI, без записей |
| Локальный сейв | каждые ~30 сек + значимые действия | `localStorage` | всегда свежий, не зависит от сети |
| Облачный сейв | ~раз в 3 мин + pagehide/signOut/смена персонажа | Supabase (upsert `characters.save_data`) | восстановление, синхронизация |

- В облако пишем **один снапшот** (`save_data` jsonb) целиком — дёшево.
- **При старте:** если локальный сейв новее облачного → берём локальный и пушим его в облако.
- **На `pagehide`/`visibilitychange`** обязательно облачное сохранение (иначе потеряем
  до 3–5 мин при закрытии). На мобильном то, что надёжнее `beforeunload`.
- Сжатие `save_data` через `lz-string` — опция (уже в зависимостях), уменьшит размер/ускорит запись.
- **Гость** остаётся в `sessionStorage` (сессия), облако не трогаем.

### Красные флаги / грабли
- Не писать в БД каждый тик — это убьёт производительность на 10000+ игроков.
  Буферизация (локально) + пакетный upsert (облако) — правильный путь.
- При старте всегда сверять даты локального и облачного сейва, чтобы не потерять
  свежий прогресс после перезагрузки проекта.

## 6. Характеристики / профессии / скиллы — НЕ путать

Данные понятия в коде сейчас (и в Melvor-наследии) свалены в «навыки». Их разделяем:

- **Профессии** (есть сейчас: лесорубство, рыбалка, шахта, крафт, огонь...) — дают доступ
  к предметам/рецептам **и** пассивные бонусы (HP/защита/уворот/удача — настраиваем позже).
- **Характеристики** (сила, ловкость, интеллект, удача...) — проектируем С НУЛЯ,
  источник бонусов: раса (2+/1−) + профессии (пассивные) + экипировка (будущее).
- **Скиллы** (пассивные/активные умения) — проектируем С НУЛЯ.

**В Этап 4 входит только:** единый перс (ник+аватар+раса), схема БД, структура бонусов расы,
время в карточке. Полноценные характеристики/скиллы/формулы — в СЛЕДУЮЩИЕ этапы.
На экране создания показываем «превью» из существующей системы (боевой уровень, HP).

## 7. Онбординг-поток

**Новый игрок:**
заставка → (интро-заглушка, опционально) → **регистрация** (без поля «Имя») →
**правила** (галочка «Я принимаю правила» + «Продолжить») →
**создание персонажа** (раса → 6 аватаров → ник + превью) →
**«Что нового»** → игра.

**Возвращающийся игрок:**
заставка → авторизация/восстановление сессии → **экран выбора персонажа** →
(выбор готового ЛИБО «Создать нового» с двойным подтверждением удаления старого) →
**«Что нового»** → игра.

**Гость:** заставка → гостевой режим сразу (без персонажей/правил, как сейчас).

### Окно правил
- Показывается **после регистрации** (привязано к аккаунту), не анониму.
- Храним `rules_accepted_at` + `rules_version` в `profiles` (или `user_metadata` как fallback).
- Если правила обновились — просим принять заново.

### Интро-превью (отложено, но фундамент)
- Кинопревью мира СЕЙЧАС НЕ ДЕЛАЕМ. Закладываем **точку расширения**: необязательный
  шаг «интро» в онбординге (сейчас скрыт/пропускается, дефолтный фолбэк).
  Позже в него легко вставить либо CSS-сцену из текущего арта (Ken Burns + тизер),
  либо настоящий ролик (MP4/WebM) с fallback на арт.

## 8. Отображение персонажа в игре

- **Dashboard/Sidebar:** активный перс (аватар + ник + раса) + кнопка «Сменить персонажа».
- **Экран выбора персонажа — красивый:** фон (арт), специальные карточки
  (аватар + ник + раса + **общее время**), кнопки, эффекты. Общее время — здесь,
  чтобы украсить интерфейс выбора.
- **Settings:** просмотр перса, «Сменить ник/аватар» (1 раз бесплатно), «Создать нового»
  (двойной confirm), «Удалить персонажа».

## 9. Удаление персонажа — жёсткое, с защитой и короткой страховкой

- «Создать нового» / «Удалить» — **не с первого тапа**. Вход только из Settings,
  затем **двойное подтверждение**: модал «Персонаж будет удалён БЕЗВОЗВРАТНО» + кнопка
  «Удалить и создать нового» (красная) + «Отмена». Крупные кнопки на телефоне.
- **Восстановление:** мягкое удаление `is_deleted` + `deleted_at`, данные храним **не более
  1 месяца**, потом забываем навсегда. Старые данные персонажа (ник, аватар, снапшот) и
  **донат-валюта на аккаунте** не теряются; при удалении теряется только персонаж+инвентарь.
- Никакой полноценной бэкап-системы — только лог факта удаления + прежний снапшот (TTL).
